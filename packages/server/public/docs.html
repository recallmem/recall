Recall docs

Recall is a memory layer for AI agents. You send it the messages your agents exchange with people; it works out what is true about each person, keeps track of what changed, and answers questions about them. It has a REST API, TypeScript and Python SDKs, a command line and an MCP server.

Building an app? Start with the quickstart. Giving a coding agent a memory? Go to integrations. Running it on your own servers? See self-hosting.

Quickstart

1. Get an API key. Sign in with your email, open API keys and create a key. It is shown once; keep it in your secret store.

2. Point your environment at Recall.

export RECALL_URL=https://api.recallmem.dev
export RECALL_API_KEY=pk_live_...

3. Record a conversation. Workspaces, sessions and peers are created on first use.

curl $RECALL_URL/v3/workspaces/my-app/sessions/chat-1/messages \
  -H "Authorization: Bearer $RECALL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"messages":[
        {"peer_id":"alice","content":"I moved to Utrecht last month and I am vegetarian now."},
        {"peer_id":"assistant","content":"Noted! Utrecht has great veggie food."}
      ]}'

4. Ask about the person. Learning runs in the background. New messages wait briefly so that a conversation is read in batches, so a single message is usually learned from within about 20 seconds. GET /v3/workspaces/my-app/queue/status shows progress; in a test or a script, GET /v3/workspaces/my-app/queue/status?wait_ms=30000 starts the waiting work at once and answers when it is done (it waits at most 60 seconds), and the SDKs do the same with waitForIdle() (wait_for_idle() in Python). Prompt context always includes the newest messages, learned from or not.

curl $RECALL_URL/v3/workspaces/my-app/peers/alice/chat \
  -H "Authorization: Bearer $RECALL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"What should I cook for Alice?","reasoning_level":"low"}'

{"content":"Something vegetarian — she switched to a vegetarian diet...",
 "citations":["..."],"confidence":0.9,"abstained":false}

5. Look at what it learned. Open the dashboard: Memory lists the facts Recall concluded about Alice, with when each held and the messages it came from.

Concepts

ThingWhat it is
WorkspaceAn isolated memory space, usually one per app or environment.
PeerAnyone who speaks: a user, an agent, a bot. Use one stable id per real person or agent.
SessionOne coherent conversation between peers. Messages belong to a session.
ConclusionA fact Recall derived about a peer, as seen by an observer, with when it became true, when it stopped, and the messages it came from.
Peer cardA short, always-up-to-date profile of a peer: the facts worth having in every prompt.
ScopeA group of sessions you want to recall together, e.g. one project or one customer account.
Night shiftA background pass after a conversation goes quiet, once enough new facts have built up: it merges duplicates, closes facts that changed, draws new conclusions with their sources and rewrites the peer card. At most three model calls, included in the price. The API calls it a dream; POST …/schedule_dream runs one at once.
Facts are bi-temporal. When Alice says she moved, "lives in Amsterdam" is closed and "lives in Utrecht" starts — at ingest, with relative dates like "last week" anchored to when the message was written.

Switching to Recall

Recall implements the v3 memory REST API (workspaces, peers, sessions, messages, chat and context), so a client written for it keeps working: point its base URL at Recall and use a Recall key. Nothing else changes in your code. The switching guide lists the few differences in behaviour and a checklist.

# the two settings to change in your existing client
base URL  https://api.recallmem.dev
API key   your Recall key (pk_live_...)

What you get on top: answers with citations, confidence and abstained; facts that are superseded at ingest instead of later; an Idempotency-Key header that makes retried writes and questions safe; POST …/sessions/{id}/turn to store messages and get context in one request; usage by task at GET /v3/usage; read-only GETs for one workspace, peer or session; and DELETE …/peers/{peer} to forget a person.

Ask questions

POST /v3/workspaces/{workspace}/peers/{peer}/chat answers a question from what the peer knows. Ask about another peer with target, restrict to a conversation with session_id, and stream with "stream": true.

FieldMeaning
queryThe question, in plain language.
reasoning_levelminimal, low (default), medium, high or max. Up to medium: one retrieval and one model call. High and max use a tool loop for hard, multi-step questions. On the hosted service Recall Loom answers at minimal and Recall Lumen at low to max (levels compared).
include_evidenceAlso return the facts and messages the answer used.
response_formatA JSON Schema: the answer comes back as matching JSON.

Answers are cached until the memory they depend on changes; a cached answer is still billed as one query. To make a retry safe, send an Idempotency-Key header: the same key with the same request returns the first answer again, without asking or charging a second time. See retries.

Prompt context

GET /v3/workspaces/{workspace}/sessions/{session}/context?tokens=4000&peer_target=alice returns recent messages, a running summary and what is known about the peer, trimmed to your token budget. With search_query it adds the facts most relevant to the current turn. The SDKs turn it into OpenAI or Anthropic messages for you.

SDKs

Recall ships typed SDKs for TypeScript and Python with lazy handles (no request until you use them), idempotent writes, retries with backoff, and prompt builders.

import { Recall } from "@recall-memory/sdk";

const recall = new Recall();             // RECALL_URL, RECALL_API_KEY
const alice = recall.peer("alice");
const session = recall.session("chat-1");

const { context } = await session.turn([alice.message("Hi again!")], {
  peerTarget: alice, tokens: 4000,
});
const messages = context.toOpenAI(recall.peer("assistant"));

Install. TypeScript: npm install @recall-memory/sdk. Python: pip install recall-mem (you import it as recall_memory). Both are open source under the MIT licence, in packages/sdk and sdks/python of the repository. Any other client for the v3 API works unchanged too; see Switching to Recall.

Both SDKs also have peer.delete() to forget a person.

Command line

recall is the command-line client for a Recall server, and it can run one too. It is part of the server's source code, not a package on npm, so you get it from the repository:

# from a checkout (Node 22 and pnpm 10)
git clone https://github.com/recallmem/recall && cd recall
pnpm install && pnpm --filter @recall-memory/server build
alias recall="node $PWD/packages/server/dist/cli.js"

# or inside the Docker image, where it is on the PATH (see self-hosting)
docker compose exec recall recall doctor

You do not need it to use the hosted service: the dashboard, the SDKs and the integrations do the same things. Save the connection once, then look at and edit memory:

recall init --url $RECALL_URL --api-key $RECALL_API_KEY -w my-app -p alice
recall doctor --url $RECALL_URL        # check the key, workspace, queue and peer
recall peer card                       # what Recall knows about you
recall peer chat "Where do I live?"
recall session messages <id> --last 10
recall conclusion create "Prefers tabs over spaces"
recall session upload notes.pdf <id> -p alice   # a file becomes messages
recall queue status                    # still learning from recent messages?
recall peer delete alice --yes         # forget a person
GroupCommands
workspacelist, create, inspect, delete, chat, search, queue-status
peerlist, create, inspect, card, chat, search, representation, get-metadata, set-metadata, dream, delete
sessionlist, create, inspect, messages, context, summaries, search, representation, peers, add-peers, remove-peers, get-metadata, set-metadata, upload, delete
scopelist, create, inspect, sessions, status, add-sessions, remove-session
messagelist, create, get

Settings come from flags, then RECALL_URL, RECALL_API_KEY, RECALL_WORKSPACE_ID and RECALL_PEER_ID, then ~/.recall/config.json. Other services' variables and config files are never read, so their keys cannot reach Recall. recall config shows each value and where it came from. Every command takes --json, and commands that delete need --yes.

recall doctor prints the configuration a server would start with (secrets are never shown): the database, which provider keys are set and the model each task routes to. With --url it also checks a running server the way a client would: /health, your API key, the workspace and its background queue, and the peer. It only reads, and exits 1 when a check fails. recall start, token, accounts and keys are for running a server.

Integrations

Recall plugs into coding agents and assistants so they remember you across sessions and projects. An integration recalls (adds your peer card and the facts Recall has learned about you to the agent's context), records (stores your messages and the agent's final replies, so Recall keeps learning) and, where the agent supports it, adds tools. The agent is a peer that Recall does not observe, so facts are learned about you, not from the agent's own statements.

AgentConnects throughMemory is added
Claude CodePlugin: hooks and MCPat session start
CodexPlugin or installer: hooks and MCPat session start
OpenClawPluginbefore each turn
Hermes AgentMemory providerbefore each turn
Agent SkillA SKILL.md the agent readswhen the agent decides to look
Any MCP clientMCP serverwhen the model calls a tool

Connect to your server. Every integration needs the URL of your Recall server and an API key, and optionally a workspace and a peer id for you. Set RECALL_URL, RECALL_API_KEY, RECALL_WORKSPACE_ID and RECALL_PEER_ID, or save them once in ~/.recall/config.json (readable only by you, chmod 600; the command line's recall init writes the same file):

{"url": "https://api.recallmem.dev", "apiKey": "pk_live_...", "workspace": "my-workspace", "peer": "your-name"}

With neither, an integration uses the hosted API at https://api.recallmem.dev, the workspace default and your OS user name as your peer id. For a server of your own, set its URL, for example http://localhost:8000; one with authentication off needs no key. Keep the peer id stable: it is how Recall knows you.

Recording sends your prompts and the agent's final replies, each cut to 24,000 characters, to the Recall server you configured. Tool calls and their output are not sent. The plugins and the Hermes provider can stop recording (RECALL_RECORD=false).

If Recall is unreachable, the plugins and the Hermes provider fail quietly: they skip it for a minute, keep what could not be sent, and deliver it in order once Recall is back. The agent behaves as it would without them.

Claude Code

The plugin recalls when a session starts, resumes or is compacted, records each prompt and Claude's final reply in a Recall session named cc-<claude session id>, and adds Recall's MCP tools. It needs Claude Code with plugin support and Node 18+.

/plugin marketplace add recallmem/recall-plugin
/plugin install recall-memory@recall

From a shell, claude plugin marketplace add recallmem/recall-plugin and claude plugin install recall-memory@recall do the same. When you enable the plugin, Claude Code asks for your Recall API key and keeps it in your system's credential store; change it, the server URL, the workspace and your name under /plugin → recall-memory → Configure. The URL, workspace and peer can also come from RECALL_URL, RECALL_WORKSPACE_ID, RECALL_PEER_ID or ~/.recall/config.json; the key only ever comes from the plugin's setting, never from files or the shell.

Restart Claude Code (or run /reload-plugins) and run /recall-memory:status: it prints the settings in use and whether the server answers and accepts your key. /mcp shows whether the recall tools connected.

Setting (default)What it does
RECALL_LOOKUP (session)session adds memory at session start; prompt also looks up facts related to each prompt; off turns lookup off.
RECALL_RECORD (true)false stops recording; lookup still works.
RECALL_CONTEXT_TOKENS (1500)Size of the memory added to the session.
RECALL_MCP_PROFILE (default)full exposes all 40 MCP tools instead of the curated eight.
RECALL_SESSION_STRATEGY (per-session)per-directory records every session of a project into one Recall session.
RECALL_ENABLED (true)false turns the hooks off. Set it under env in a project's .claude/settings.json to switch Recall off for that project.

Check it. Send Claude a prompt, then look at what was recorded, on the dashboard's Memory page or with the command line; in a new session ask "what do you know about me?".

recall session list
recall session messages cc-<session id> --last 2

Hooks never print errors into the session; they log to hooks.log in the plugin's data directory (RECALL_DEBUG=1 also prints them to stderr). Full reference: integrations/claude-code.

Codex

The Codex integration uses Codex hooks (SessionStart, UserPromptSubmit, Stop) and a stdio MCP server: it adds your peer card and facts at session start (also after /clear or a compaction), records each prompt and Codex's final reply in a session named codex-<codex session id>, and adds the same eight MCP tools. It needs Codex CLI with hooks (tested with 0.162.0) and Node 18+. Pick one of the two routes; installing both handles every turn twice.

As a Codex plugin:

codex plugin marketplace add recallmem/recall-plugin
codex plugin add recall-memory@recall

Start Codex and run /hooks: Codex skips new hooks until you trust them, so trust the three Recall hooks.

With the installer (no plugin system needed):

git clone https://github.com/recallmem/recall-plugin
node recall-plugin/integrations/codex/install.mjs \
  --url https://api.recallmem.dev --api-key pk_live_... --workspace my-workspace --peer your-name

It copies the scripts to ~/.codex/recall/scripts, adds the three hooks to ~/.codex/hooks.json and the recall MCP server to ~/.codex/config.toml (in a marked block; your other settings are untouched), and saves the connection to ~/.recall/config.json. Run it again to update, or with --uninstall to remove everything it added; then start Codex and trust the hooks with /hooks. Other options: --codex-home DIR, --no-hooks, --no-mcp, --skill (also installs the Agent Skill) and --agents-md (adds a short "Recall memory" section to ~/.codex/AGENTS.md).

The settings are the same as for Claude Code, except that RECALL_ASSISTANT_PEER defaults to codex. Codex's hook output limit is about 2,500 tokens, so keep RECALL_CONTEXT_TOKENS at or below that.

Check it.

codex mcp list                                # shows the recall server
codex exec "I prefer pnpm over npm"           # prints "session id: <id>"
recall session messages codex-<id> --last 2   # your prompt and Codex's reply

If nothing is recorded, the hooks are probably not trusted yet: run /hooks in Codex. Full reference: integrations/codex.

OpenClaw

A plugin that adds what Recall knows about you, focused on the message at hand, before each turn (in a <recall-memory> block marked as background information, not instructions), records your message and the assistant's reply after each turn in a session named oc-<session key>, and gives the assistant four tools: recall_search, recall_ask, recall_remember and recall_forget. It runs next to OpenClaw's own memory and does not take the memory slot. It needs OpenClaw 2026.9.9 or later and is installed from a checkout, because it is not on ClawHub or npm yet.

git clone https://github.com/recallmem/recall-plugin
openclaw plugins install ./recall-plugin/integrations/openclaw --force --accept-capabilities

Both hooks read the conversation, which OpenClaw only allows a third-party plugin to do once you grant it. Then say where Recall is:

openclaw config set plugins.entries.recall-memory.hooks '{"allowConversationAccess":true}' --strict-json --merge
openclaw config set plugins.entries.recall-memory.config \
  '{"url":"https://api.recallmem.dev","workspace":"my-workspace","peer":"your-name"}' --strict-json --merge

Put the API key in RECALL_API_KEY in the Gateway's environment, or in ~/.recall/config.json, rather than in openclaw.json. Restart the Gateway, or run openclaw plugins reload recall-memory. The plugin's lookup setting chooses when memory is added: turn (default) on every user turn, first-turn once per session, off for tools only. Heartbeat and cron turns are not recorded unless you set recordAutomated.

Check it.

openclaw plugins inspect recall-memory --runtime --json      # lists the four recall_* tools
openclaw agent --local -m "I moved to Utrecht last month" --session-key agent:main:recall-check
recall session messages oc-agent-main-recall-check --last 2   # your message and the reply

Full reference: integrations/openclaw.

Hermes Agent

A memory provider for Hermes Agent. Hermes' own MEMORY.md and USER.md memory keeps working; Recall is the one external provider next to it. Before each turn it returns your peer card and the facts most related to the message, after each turn it stores the exchange in a session named hermes-<session id>, it copies the facts Hermes' built-in memory saves about you, and it adds the tools recall_search, recall_ask, recall_remember and recall_forget. It uses only the Python standard library.

git clone https://github.com/recallmem/recall-plugin
mkdir -p ~/.hermes/plugins
cp -r recall-plugin/integrations/hermes/recall ~/.hermes/plugins/recall
hermes memory setup        # pick "recall" and enter the URL, API key, workspace and your peer id

hermes memory setup writes the API key to ~/.hermes/.env (RECALL_API_KEY) and the rest to ~/.hermes/recall.json. Instead of the wizard you can set memory.provider: recall in ~/.hermes/config.yaml.

Check it.

hermes memory status                               # "recall ... ← active"
hermes chat -q "I moved to Utrecht last month" -Q  # prints session_id: <id>
recall session messages hermes-<id> --last 2       # your message and the reply

Then, in a new chat, ask "where do I live?". Full reference: integrations/hermes.

Agent Skill

A portable skill in the Agent Skills format: a folder with a SKILL.md that teaches any agent that supports skills when and how to use Recall. It looks up what is known about the user, saves facts they state, forgets on request, and records conversations when nothing else does. It works through Recall's MCP tools when they are connected, and otherwise through scripts/recall.mjs, a dependency-free Node 18+ helper. Nothing happens automatically: the agent reads the skill when a task calls for memory and decides what to call. Use it alone or next to an integration; the skill tells the agent not to record messages itself when an integration already does.

Copy the recall-memory folder to where your agent looks for skills:

git clone https://github.com/recallmem/recall-plugin
mkdir -p ~/.agents/skills && cp -r recall-plugin/integrations/agent-skill/recall-memory ~/.agents/skills/
AgentPersonal skills folder
Claude Code~/.claude/skills/
Codex~/.agents/skills/, or run the Codex installer with --skill
OpenClaw~/.agents/skills/, or <workspace>/skills/ for one agent
Hermes Agent~/.hermes/skills/, or add ~/.agents/skills to its external skill directories

The skill needs no configuration when the agent has Recall's MCP tools. For the helper script, set the usual variables or write ~/.recall/config.json (see connect to your server). Check it:

node ~/.agents/skills/recall-memory/scripts/recall.mjs status        # health ok, access accepted
node ~/.agents/skills/recall-memory/scripts/recall.mjs remember "Prefers tea over coffee"
node ~/.agents/skills/recall-memory/scripts/recall.mjs context --query drinks

Then ask your agent "what do you remember about my drinks?". Full reference: integrations/agent-skill.

MCP

Recall serves the Model Context Protocol at https://api.recallmem.dev/mcp (streamable HTTP, stateless). By default it exposes eight tools for recording and recalling: chat, search, get_session_context, get_peer_card, list_conclusions, create_conclusions, delete_conclusion and add_messages_to_session. Use /mcp?profile=full (or send x-recall-mcp-profile: full) for all 40 tools (workspaces, peers, sessions, conclusions, scopes). There are two ways to connect: sign in from the app (hosted Recall), or send an API key.

Add Recall as a connector

Apps that support remote MCP servers with OAuth sign in to Recall themselves: you paste the URL, sign in with your email, choose what the app may use and approve. No API key is copied anywhere.

  • Claude (claude.ai, Desktop and mobile share connectors): Settings, Connectors, Add custom connector. Name it Recall, enter https://api.recallmem.dev/mcp, leave the OAuth client fields empty and choose Add, then Connect. In a chat, switch Recall on in the tools menu.
  • ChatGPT: turn on developer mode (Settings, Apps & Connectors, Advanced settings), then create a connector with the same URL and OAuth authentication, and sign in when ChatGPT asks.
  • Claude Code: claude mcp add --transport http recall https://api.recallmem.dev/mcp, then run /mcp and choose Authenticate.
  • Cursor, VS Code and other clients: add a remote (streamable HTTP) MCP server with that URL and no headers; the client finds the sign-in at /.well-known/oauth-protected-resource.

A browser window opens on Recall. Sign in with the emailed link (it brings you back), then on Connect an app check the app's name and where it sends you back to, pick the account, the default workspace (used when a tool names none), whether the app may also use other workspaces or all of them, and optionally a default peer: who "I" am in this memory, usually your name. Remember automatically is ticked: the app then saves lasting facts you share (preferences, plans, people) without being asked. Untick it to have the app save only what you ask it to; you can change it later under API keys → Connected apps. Choose Allow.

The app then works with the reach you chose, under the same rate limits, budget and credit as an API key. Its tokens renew themselves; a connection unused for 30 days has to sign in again. See and revoke connections in the dashboard under API keys, Connected apps: a revoked app is signed out within seconds. Connected apps reach only the MCP endpoint, never the REST API, your keys, billing or settings. Only owners and admins of an account can connect apps to it.

Approve only connections you started yourself. If the consent screen says the app sends you back to localhost, any program on your computer could be asking: continue only if you just connected from an app on this device.

With an API key

Clients that can send headers can use a key instead (self-hosted servers, which have no sign-in, always do). Defaults for the workspace, your peer id and the session then come from the headers X-Recall-Workspace-ID, X-Recall-User-Name and X-Recall-Session-ID.

{
  "mcpServers": {
    "recall": {
      "type": "http",
      "url": "https://api.recallmem.dev/mcp",
      "headers": { "Authorization": "Bearer pk_live_..." }
    }
  }
}

Webhooks

Register an endpoint with POST /v3/workspaces/{workspace}/webhooks and a body of {"url": "https://…"}. Recall sends a queue.empty event when background work for a session finishes; GET …/webhooks/test sends a test.event. A workspace can have 10 endpoints, and URLs that point at private addresses are refused.

POST https://your-endpoint.example/recall
X-Recall-Signature: <hex HMAC-SHA256 of the body>
X-Recall-Event-Id: <event id>

{"data":{"observed":"alice","observer":"alice","queue_type":"representation",
 "session_id":"chat-1","workspace_id":"my-app"},
 "timestamp":"2026-10-09T10:00:00Z","type":"queue.empty"}
  • Verify the signature. X-Recall-Signature is the hex HMAC-SHA256 of the raw request body, keyed with your webhook secret: your account's own secret (rotate it under Settings). The body is compact JSON with sorted keys, so verify the bytes you received.
  • Drop duplicates. X-Recall-Event-Id is the same on every retry of an event, so keep the ids you have handled and ignore repeats.
  • Answer quickly with a 2xx. Recall retries with backoff when your endpoint cannot be reached, times out, or answers 5xx, 408 or 429. Other 3xx and 4xx answers are final.

Self-hosting

You can run Recall yourself. The server is source-available under the Functional Source License (FSL-1.1-ALv2): you may run it in production for your own products and company, with your own model provider keys, and change it; what it does not allow is offering it to others as a memory service that substitutes for Recall. Each version becomes Apache 2.0 two years after its release. The SDKs and integrations are MIT. The hosted service runs the same server and is the easiest path, with nothing to operate. The code is at github.com/recallmem/recall.

With Docker Compose: Postgres with pgvector, and Recall on port 8000.

git clone https://github.com/recallmem/recall && cd recall
cp .env.example .env        # add a model provider key; every setting is explained there
docker compose up --build
curl localhost:8000/health

One container, with an embedded Postgres kept in a volume: good for a laptop, a demo or a small agent.

docker build -t recall-server .
docker run -p 8000:8000 -v recall-data:/data -e OPENAI_API_KEY=sk-... recall-server

From source (Node 22 and pnpm 10): pnpm install, then pnpm dev runs the server with reload on port 8000; for production, pnpm --filter @recall-memory/server build and node packages/server/dist/main.js. Without RECALL_DATABASE_URL the server keeps an embedded Postgres in ./.recall; any Postgres 16 or later with pgvector works through that setting.

Point clients at your server with RECALL_URL=http://localhost:8000 (in the SDKs, baseURL or base_url; in the integrations, their server URL setting). With no provider key the server runs on an offline mock model: the API, storage and search are real and the answers are canned, which is enough to try it. Set a key and choose models as described in models and providers.

Authentication is off by default, so a local server needs no key. Before anyone else can reach it, set RECALL_AUTH_ENABLED=true and a long random RECALL_AUTH_SECRET, then give each client a token from the command line, scoped to a workspace (and optionally a peer or session), or --admin for everything:

docker compose exec recall recall token --workspace my-app

Compared with the hosted service, a server of your own has no sign-in, dashboard or billing (those belong to its multi-tenant hosted mode), so MCP clients connect with a token in a header instead of signing in; usage shows your real providers, models and cost; and how good the memory is depends on the models you choose. The benchmark figures were measured on the hosted service, and evals/ in the repository measures your own setup.

REST API

The Recall tag marks endpoints beyond the standard v3 API.

Read without creating

POST /v3/workspaces, POST …/peers, POST …/sessions and the PUTs on a peer or a session get or create, so a typo in an id quietly makes something new. To only look, use GET:

GET /v3/workspaces/{workspace}
GET /v3/workspaces/{workspace}/peers/{peer}
GET /v3/workspaces/{workspace}/sessions/{session}

Each returns the same object as the get-or-create call and never creates anything. A workspace, peer or session that does not exist answers 404; the hidden peer id of a scope answers 422.

Search filters

The three search routes take query, limit (1 to 100, default 10) and filters. Besides field and metadata filters, filters accepts peer_perspective: a peer id. Results are then limited to what that peer saw, meaning messages in sessions it belongs to (or belonged to) that were written while it was a member, plus everything it wrote itself.

curl $RECALL_URL/v3/workspaces/my-app/search \
  -H "Authorization: Bearer $RECALL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"tent","filters":{"peer_perspective":"bob"},"limit":10}'

peer_perspective must be a non-empty peer id, otherwise the request is a 422. A peer that does not exist saw nothing, so the result is empty.

Retries and Idempotency-Key

A request can time out after the server did the work. To retry without doing it twice, send an Idempotency-Key header (up to 255 characters, for example a UUID per logical request) and send the same key with the retry:

  • Messages (POST …/messages, POST …/messages/upload, and the messages of POST …/turn): the same key with the same messages returns what the first request stored, and nothing is stored twice. The same messages means the same authors, content, metadata, configuration and created_at, in the same order. The same key with different messages answers 409.
  • Chat (POST …/chat): the same key with the same request returns the first answer again, with the same status and body and the header Idempotent-Replayed: true. Nothing is asked or charged a second time. A streamed answer comes back as the same stream. If a stream breaks off, retry with the same key: the answer was finished and comes back whole. The same key with a different question or settings answers 409, and so does the same key while the first request is still running (retry shortly). A request that produced no answer (an error, or an answer from empty memory) is not kept, so the same key can try again.

Chat answers are kept for 24 hours; after that the key counts as new. A chat key belongs to the API key that sent it, so two API keys never share one.

The SDKs add a key to every write, so their own retries are always safe; pass your own (idempotencyKey, or idempotency_key in Python) when another process might send the same write again.

Add facts yourself

Recall learns facts from messages, but you can also store facts you already know, such as a plan from your billing system or a preference set in your app. observer_id is whose view the fact belongs to and observed_id who it is about; for what Recall knows about a person, both are that person. session_id is optional. Send 1 to 100 facts of up to 65,535 characters each; the answer is 201 with the stored facts and their ids.

curl $RECALL_URL/v3/workspaces/my-app/conclusions \
  -H "Authorization: Bearer $RECALL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"conclusions":[{"content":"Is on the Team plan since March 2026",
                     "observer_id":"alice","observed_id":"alice"}]}'

A fact that the same view already holds as a current fact, with the same text apart from case and spacing, is not stored twice. The answer has the stored fact, with times_derived one higher. Recall does the same with facts it learns from messages.

Facts and their history

POST …/conclusions/list pages through facts, newest first. POST …/conclusions/query finds the facts closest in meaning to query in one view, so its filters must name observer_id and observed_id. Both also return facts that no longer hold, so you can see how something changed. A fact looks like this:

{"id":"Hq3…","content":"alice lives in Rotterdam","observer_id":"alice","observed_id":"alice",
 "session_id":"chat-1","level":"explicit","source_ids":[],"times_derived":1,
 "created_at":"2026-09-01T09:00:04.512Z","valid_from":"2026-09-01T09:00:00.000Z",
 "valid_to":"2026-09-20T09:00:00.000Z","superseded_by":"Vt8…","message_ids":["Kp2…"]}
FieldMeaning
levelexplicit: said outright, or added by you. deductive, inductive or contradiction: drawn from other facts.
source_idsThe facts a drawn fact was drawn from. Empty for explicit facts.
times_derivedHow often the fact was learned or stated.
valid_fromRecallWhen the fact started to hold: the time of the message it was learned from, or when you added it.
valid_toRecallWhen it stopped holding. null while it is current.
superseded_byRecallThe id of the fact that replaced it, or null.
message_idsRecallThe ids of the messages it was learned from. Empty for facts you added.

To get only what holds now, filter on "current": true; false gives only the history. Without it you get both, as before.

curl $RECALL_URL/v3/workspaces/my-app/conclusions/list \
  -H "Authorization: Bearer $RECALL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"filters":{"observer_id":"alice","observed_id":"alice","current":true}}'

Both routes filter on id, workspace_id, observer_id, observed_id, session_id, level, source_ids, times_derived and metadata, and on Recall's current, valid_from, valid_to, superseded_by and message_ids. For example, {"message_ids": "Kp2…"} finds the facts learned from one message, and {"valid_to": {"gte": "2026-09-01"}} the facts that stopped holding since 1 September. Any other field answers 422.

Run the night shift now

The night shift runs by itself; POST …/schedule_dream starts one now, for example after importing a history. The answer is 204 and the work is queued.

curl $RECALL_URL/v3/workspaces/my-app/schedule_dream \
  -H "Authorization: Bearer $RECALL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"observer":"alice","observed":"alice","dream_type":"omni"}'
FieldMeaning
observerRequired. Whose memory to go over.
observedWho it is about; defaults to observer.
dream_typeRequired. omni: the full pass (merge, close, conclude, rewrite the card). card_refresh: only rewrite the peer card; with "rebuild": true from scratch.
session_idOptional: use that session's configuration for the pass.

A requested pass is free, so the same kind runs at most once every 10 minutes for the same observer and peer, and omni only when facts changed since the last pass; otherwise the request is skipped.

Forget a person

DELETE /v3/workspaces/{workspace}/peers/{peer} erases a person, for example when they ask you to under GDPR. It removes:

  • every message the peer wrote, and its memberships in sessions;
  • everything memory holds about the peer and from its point of view: facts and peer cards in every collection it observes or is observed in, including what scopes remember of it;
  • the summaries of sessions it wrote in. They quote it, so they are dropped and rebuilt from the remaining messages;
  • cached answers, which may quote it.

It keeps facts about other peers that merely mention the person, and messages other people wrote. Delete those separately if you need them gone: DELETE …/conclusions/{id}, or the session with DELETE …/sessions/{session}.

curl -X DELETE $RECALL_URL/v3/workspaces/my-app/peers/alice \
  -H "Authorization: Bearer $RECALL_API_KEY"

{"peer_id":"alice","deleted":true,"messages_deleted":12,
 "conclusions_deleted":9,"sessions_affected":2}

The response says what was removed (the numbers here are examples). The call is permanent. It needs a key for the whole workspace or account: a key scoped to one peer or one session answers 401. A peer that does not exist answers 404, so if the response to a retry is a 404, the peer is already gone. The SDKs and the CLI do the same:

await recall.peer("alice").delete();   // TypeScript
recall.peer("alice").delete()          # Python
recall peer delete alice --yes         # CLI; --yes confirms

The TypeScript SDK returns { peerId, messagesDeleted, conclusionsDeleted, sessionsAffected }; the Python SDK returns the response as a dict.

Export your data

Settings > Export all data in the dashboard downloads everything your account stores as one JSON file, free of charge, as often as you like. Its format is recall-export-v1; the other top-level keys are:

  • exported_at, account, members, api_keys (names, scopes and dates; never a key or its hash) and connected_apps;
  • workspaces, peers, sessions and session_peers, with their metadata and configuration;
  • messages: every message with its workspace, session, peer, position in the session, content, metadata and token count;
  • collections (what one peer knows about another, with its peer card), conclusions (the facts, with confidence, sources as message ids, the period they were true and what replaced them; facts the night shift replaced have deleted_at set) and summaries;
  • webhook_endpoints (URLs, never the secret), llm_usage (model calls with token counts) and credit_ledger (every charge and top-up, in micro-USD).

Each array holds plain objects with snake_case fields (for example workspace_id, created_at); times are ISO 8601 in UTC. Embeddings are left out: they are recomputed from the text. To move to another server, replay peers, sessions and messages through the REST API; memory is rebuilt from the messages.

Browser access

By default any origin may call the API, because it authenticates with bearer keys, not cookies. If you run Recall yourself, restrict it with RECALL_CORS_ORIGINS, a comma-separated list of origins; unset, or *, allows any:

RECALL_CORS_ORIGINS=https://app.example.com,https://admin.example.com

Code that runs in a browser should hold a key scoped to one workspace, peer or session (set the scope when you create it under API keys), never an account-wide key.

A key scoped to a peer can create sessions with that peer as a member, and creating a session that already exists adds members instead of replacing them. So when you hand peer keys to your end users, give sessions ids they cannot guess (a UUID, not support-bob), or create each session with your workspace key before the user's key ever sees its id; otherwise one user could create the session another user's conversation will later go into. Keys minted with POST /v3/keys are revoked together with the key that minted them, and a pk_test_ key reaches the same data and spends the same credit as a live one: the prefix is only a label.

Errors and limits

Errors are JSON with a detail field. Usually it is a sentence: {"detail": "Workspace my-app not found"}. When the request itself is invalid (a missing field, a wrong type, a value out of range), the answer is 422 and detail is a list with one entry per problem, in the format FastAPI uses, so v3 clients parse it unchanged:

{"detail":[{"type":"too_big","loc":["body","messages",0,"content"],
  "msg":"Too big: expected string to have <=25000 characters","input":"…"}]}

input is the value you sent. A long value is cut to about 200 characters, ending in …, so a huge request never comes back in full.

A few checks made after that (such as an Idempotency-Key that is too long) also answer 422, with a sentence. Read detail as a string or a list.

StatusMeaning
401Missing or invalid key, or a key whose scope does not cover this resource. Recall never answers 403.
402Out of credit or over your monthly cap. Messages are still stored; learning and chat resume after a top-up.
404Not found.
409Conflict: an Idempotency-Key sent again with a different request or while its first request is still running, or deleting a workspace that still has sessions.
413The request body is too large (see the limits below).
422Invalid input; detail says which field.
429Rate limited; retry after the number of seconds in the Retry-After header.

Rate limits. Each API key or connected app may make 600 requests a minute, and ask 60 questions a minute (chat over REST or MCP; the dashboard's Playground counts per account). Limits are token buckets: you can burst up to the minute's allowance, which then refills steadily. After 30 failed sign-ins with a bad key from one network within a minute, further failures from there answer 429 instead of 401 for a while; valid keys keep working. Responses carry no rate-limit headers (no X-RateLimit-*), so pace yourself and, on a 429, wait for Retry-After; the SDKs do that for you.

Cost metering

Every model and embedding call is recorded with its tokens and cost, by workspace, task and model. GET /v3/workspaces/{id}/usage and GET /v3/usage report calls, input_tokens and output_tokens (the workspace usage also cache_read_tokens and cache_write_tokens), in total, by_task and by model or workspace.

On the hosted service there is no cost_usd: our provider cost is not what you pay. The workspace usage names the hosted models Recall Lumen (recall-lumen, answers at low to max), Recall Loom (recall-loom, builds memory and answers at minimal) and Recall Embed (recall-embed, embeddings). On prepaid credit, what you were charged is in billed, for the period and, at GET /v3/usage, for each workspace: billed_usd in all, learning (message_tokens billed, each message counting as at least 50, and their billed_usd) and chat (questions and billed_usd, in all and by_level). Charges given back are left out, so it matches the credit history under Billing.

On a server of your own, cost_usd is the provider cost and unpriced_calls counts calls to models with no known price; there is no billed. OpenRouter reports what it charged for each call and Recall records exactly that; on your own provider key (BYOK) it adds the upstream provider's charge OpenRouter reports, and prices the call's tokens at list price when that charge is missing. For other providers the cost is the call's tokens at list price, cache reads and writes included; override prices with RECALL_PRICING_JSON. OpenRouter models missing from Recall's price table are priced from OpenRouter's public catalog (turn that off with RECALL_OPENROUTER_LIVE_PRICES=false).

Pricing

Prepaid credit, no subscription. New accounts get $5. Learning from messages costs $1.75 per 1M message tokens, a message counting as at least 50 tokens. A message Recall reads without learning from it (from a peer you do not observe, or in a session with reasoning off) counts only what it reads: at most 200 tokens as context, 600 for a summary. Chat costs $0.0008 (minimal), $0.005 (low), $0.025 (medium), $0.05 (high) or $0.25 (max) per query. The price is taken when the answer starts, so it never spends credit you do not have; it is given back when no answer comes, and an answer from empty memory is free. On chat, an Idempotency-Key makes a retry free: the same key with the same request returns the first answer again (see retries). Context, search, storage, summaries and dreams are included. Set a monthly cap and auto top-up under Billing. Credit is in US dollars; Checkout charges its euro amount at the European Central Bank's daily rate (or your own currency where Stripe offers it) and takes cards, iDEAL, Bancontact and other local methods.
