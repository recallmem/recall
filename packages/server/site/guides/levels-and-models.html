Reasoning levels and models

Recall gives you three ways to read memory: context, search and chat. Two of them use no model at all. This guide shows which call fits where, what the five chat levels do and cost, and how to choose the models that answer.

Context. searchQuery adds the facts most relevant to what the user just said; tokens caps the whole result. The SDKs turn it into OpenAI or Anthropic messages.

Search. Hybrid search over the stored messages, with filters. It returns what was said, not what Recall concluded.

The five chat levels

LevelHow it answersPrice per questionGood for
minimalOne retrieval of up to 8 facts, one call to Recall Loom$0.0008Single facts: "where does she live?", game and workflow logic
low (default)One retrieval of up to 24 facts, one call to Recall Lumen$0.005Everyday questions about a person
mediumOne retrieval of up to 32 facts, one call to Recall Lumen that thinks longer$0.025Questions that combine many facts: plans, summaries, comparisons
highRecall Lumen searches memory itself, in up to 3 rounds, then answers$0.05Multi-step questions across many conversations
maxUp to 6 rounds of searching by Recall Lumen, with the largest budget$0.25Rare, hard questions where the answer is worth the wait

Recall Loom and Recall Lumen are the models of the hosted service (see which models answer); on your own server each level uses the model you set for it. high and max are slower than the single-call levels, by how many steps the question needs. An answer from empty memory is free. The price is taken when the answer starts and given back if no answer comes.

Choosing a level

  • Start low, then move up only where it helps. Collect twenty real questions from your product and run them at two levels in the dashboard's Playground, which runs the same engine and shows the evidence behind each answer. Keep the lowest level that answers them correctly.
  • Choose per question, not per app. A support bot can look up the plan at minimal and write a handoff summary at medium.
  • Counting and timelines are the hard cases. "How many times did I…" and "what happened first" need many facts at once; give those a higher level or read the messages with search.
  • Never block a user on a level they do not need. In real-time products (voice, games) read context in the turn and ask questions before or after it.

Evidence and abstaining

With includeEvidence you get the facts and messages the answer used, a confidence between 0 and 1, and abstained: true when memory did not hold the answer and Recall said so instead of guessing. Show the sources to users who need to trust the answer, and handle abstentions in your code rather than passing "I don't know" to a customer.

Structured answers

Give a JSON Schema (or, in Python, a Pydantic model) and the answer comes back as matching JSON, ready for code: profile fields, a list of open issues, a yes or no with a reason.

Caching

Answers are cached until the memory they depend on changes, so asking the same question twice returns at once. A cached answer is still billed as one question; the cache saves time, not money. Sending the same Idempotency-Key with the same request returns the first answer again instead of asking a second time, so a retry after a timeout never pays twice; the same key with a different question answers 409 (see retries).

Which models answer

Recall sends each kind of work (learning from messages, summaries, peer cards, the night shift, and chat at each level) to a model chosen for it. Each can come from a different provider.

  • On the hosted service we choose the models, test candidates against public long-term memory benchmarks with the memory held fixed before changing one, and publish results on Evals. Requests go through OpenRouter only to providers that do not collect the data (see Privacy). GET …/usage shows the tokens of each kind of work by model: Recall Lumen (recall-lumen) answers questions at low to max, Recall Loom (recall-loom) builds memory and answers at minimal, and Recall Embed (recall-embed) computes embeddings.
  • When you run Recall yourself you set a model per task with environment variables such as RECALL_MODEL_REASONER and RECALL_MODEL_CHAT_LOW, from OpenAI, Anthropic, Gemini, OpenRouter, Groq, xAI, DeepSeek, Together, Fireworks or any OpenAI-compatible server. See Models and providers.

What we have learned from testing: a stronger answer model helps most on questions about timelines and on questions that combine many conversations, and thinking models can add many seconds per answer. A cheap model is fine for learning, which runs in the background, as long as it extracts dates and changes reliably.

Pitfalls

  • Asking where reading would do. If your model writes the reply anyway, context gives it the same knowledge without a second model call.
  • Using max by default. It costs 50 times low and is slower. Keep it for the questions that need it.
  • Treating an abstention as an answer. Check abstained and decide what your product does when memory does not know.
  • Asking right after storing. Learning runs in the background and usually takes about 20 seconds, because new messages are read in batches. A question asked at once may not see the newest message yet; context always includes it. In tests and scripts, waitForIdle (wait_for_idle in Python) starts the waiting work at once and returns when it is done.
